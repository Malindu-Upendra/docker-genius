# DOCKER-GENIUS — Research Status & Next Steps

**Last updated:** 2026-08-17
**Purpose:** Living record of what's actually true about the project right now, what was fixed, and what remains — so a fresh session (or your supervisor, or you in a month) doesn't have to reconstruct this from scratch.

**TL;DR (read this first):** The pipeline was broken by ~11 distinct bugs (§2) discovered and fixed between 2026-08-10 and 2026-08-17. Once fixed, two large runs (§1e, §1f) showed the three governance strategies' ranking is *not stable* across load intensity — a real, honest finding. Investigating why (§1g) found the default rule engine's step size/cooldown was too conservative for the LSTM's forecast to matter; a 5x-replicated confirmation (**§1i**) is **the headline result**: with a more aggressive rule engine, Proactive Hybrid shows a statistically defensible advantage over *both* Static (+8.1%) and Reactive (+7.3%) SLA breach reduction — real, but modest and well short of the proposal's ≥30% target. An ablation study (§1h, single-rep) suggested the semantic layer drives most of the default-settings benefit; **§1j (5x-replicated, 2026-08-17) does NOT confirm this** — properly replicated, all four ablation configs cluster within ~1.2 points of each other (well within the ~2.2-point rep-to-rep noise floor observed for a single unchanged config), and the only statistically defensible pairwise result actually shows semantic-only beating the full system, not the reverse. §1j also surfaced a cross-experiment inconsistency worth flagging in Threats to Validity: nominally-identical configs in §1i and §1j disagree by ~1-2 points and even flip which strategy wins — read as evidence of session-to-session noise in the point estimates, tempering confidence in §1i's exact magnitude (the CI-excludes-zero conclusion itself still stands). The whitelist-stripping bug pattern (§2 bug #11) has now been fixed and empirically verified across all 12 remaining endpoints (§5 item 5); a scalability-test design is drafted and ready to execute (§5 item 8/§8). See §5 for what's left (mostly paper-writing and, time permitting, the scalability test).

## 1. Current honest status

The infrastructure (ERP app, semantic tiering, LSTM pipeline, rule engine, Docker Update API integration, 3-group experiment harness, statistical analysis) is now **genuinely functional end-to-end** — verified across two full runs (2026-08-10 and 2026-08-12). Before 2026-08-10, several silent bugs meant no prior experiment run (including the July 5 run whose numbers were circulating as "the result") was actually measuring what it claimed to measure.

**§1a — Run 1 (2026-08-10, moderate-load-trained model):** Proactive Hybrid performed *worse* than Static/Reactive (19.3% SLA breach vs 13.5%/12.4%), statistically significant. Diagnosed root cause: train/serve distribution mismatch — the LSTM was trained on a moderate-load capture but evaluated under much heavier contention, so it never predicted CPU high enough to trigger scale-up (Rule 1 fired 0 times in that run).

**§1b — Run 2 (2026-08-12, retrained on matched-load telemetry — see §4 for what changed):** Fixed the train/serve mismatch by recollecting telemetry under the same load intensity used for evaluation and retraining. Rule 1 (proactive scale-up) *did* fire this time, and the LSTM forecast was in active use for 31/37 decision cycles — the mechanism is now genuinely working end-to-end. **But the result is still negative**: Proactive Hybrid showed a 20.2% SLA breach rate vs Static's 9.4% and Reactive's 16.9% (Mann-Whitney significant, breach reduction G1→G3 = ‑116%, 95% CI [‑134%, ‑101%]). This was a single, unreplicated run each.

**§1c — Run 3 (2026-08-12, 5x replicated — see §6 for two new infra bugs found along the way):** Extended `run_experiment.py` with `--repeats N` (pools each group's KPI CSVs across reps into the same `group{N}_kpi.csv` mann_whitney.py already reads; per-rep breakdown saved to `experiment_reps_summary.txt`). Ran the full 5x300s×3-group sequence successfully end to end (~2 hours). **But the pooled result is not usable as a headline finding**: all three groups converged to nearly identical numbers (Static 18.4%, Reactive 17.9%, Proactive 18.9% breach; P95/P99 all clustered at ~5000ms across all three groups). Root cause: `mixed_load.py`'s Tier-1 checkout request uses a 5-second client timeout, and by the later reps enough requests were hitting that ceiling (4.3% of all Tier-1 requests landed at 4900-5100ms) that it dominates the tail statistics uniformly across groups, erasing any real differentiation. Compounding cause: `invoices`/`invoice_items` are never truncated between reps (only `semantic_request_logs` is), so the transactional dataset — and therefore report-query cost — kept growing across all 5 reps instead of each rep starting from an identical baseline. **This data should not be cited as evidence for or against the hypothesis.** See §5 item 1 for the fix before re-attempting replication.

**§1d — Run 4 (2026-08-13, two more fundamental fixes, see §2 bugs #10-11):** Attempted a corrected 5x-replication run with the §1c fixes (25s checkout timeout, transactional-data reset between reps) applied. First rep showed breach rates of 0.35%/2.32%/1.9% across Static/Reactive/Proactive — far too low to be meaningful, and Static (no adaptation) showed the *lowest* rate, which is a strong signal these are just noise. Investigated with `docker stats` during a live burst and found the actual reason: **`erp_app` sat at 32-42% CPU while `erp_mysql` hit 82-112%** — the "heavy" Tier-3 endpoints were pure SQL delegated to a separate MySQL container, so no amount of that load could ever raise `erp_app`'s own CPU (the only thing the governor monitors/scales) high enough to matter. Separately found that `research_mode` had been silently `undefined` on **every single bulk-generate call ever made**, because NestJS's global `ValidationPipe({whitelist: true})` strips `@Body()` properties on inline TypeScript types (no reflection metadata) — masking a CPU-burn feature that hadn't even been wired correctly yet at that point. Fixed both: added genuine CPU-bound synchronous computation to `bulkGenerate` (gated correctly behind `research_mode` now, via a real DTO class with `class-validator` decorators), calibrated to ~3s per call, verified with `docker stats` that this now visibly loads `erp_app` itself (mean CPU 90.7%, peak 126.6% in a fresh telemetry capture) and, in a governor smoke test, correctly drove **Rule 1 to fire 5 times, escalating cpus 1.5→4.0** in direct response. Retrained the LSTM on this new signal, then ran the full 5x-replicated experiment.

**§1e — Run 4 results (2026-08-13, THE FIRST VALID RESULT — cite this one):** Pooled across 5 reps (n≈5,200-5,500 TIER_1 requests per group):

| Group | Mean | P50 | P95 | P99 | Breach% |
|---|---|---|---|---|---|
| Static Allocation | 2100.4ms | 2869.8ms | 3935.2ms | 6405.1ms | 65.5% |
| Reactive-Only | 2196.6ms | 2864.0ms | 3863.0ms | 9756.1ms | 68.2% |
| Proactive Hybrid | 2068.3ms | 2854.6ms | 3737.8ms | 5755.4ms | 66.1% |

Mann-Whitney U is "significant" for both G1-vs-G3 and G2-vs-G3 (p<0.00001) but with **negligible effect size** (r≈-0.05 to -0.06) — at n≈5,500 per group, even a trivial shift reaches significance, so p-value alone is misleading here; the effect size and bootstrap CI are the numbers that actually matter:
- **G1 (Static) → G3 (Proactive): -0.8% breach reduction, 95% CI [-3.5%, +1.9%]** — the CI spans zero, so this run **cannot distinguish Proactive from Static**. The original ≥30% SLA-reduction hypothesis is **not supported** by this data.
- **G2 (Reactive) → G3 (Proactive): +3.2% breach reduction, 95% CI [+0.6%, +5.6%]** — this CI does *not* cross zero: a small but real, statistically defensible improvement of Proactive over pure Reactive governance.
- Reactive-Only showed by far the highest rep-to-rep variance (breach% ranged 64.0%-79.9% across the 5 reps, a 15.8-point spread) vs Static's 3.4 points and Proactive's 5.4 points — Proactive's forecast-driven approach produced *more consistent* outcomes even where the mean improvement was small.
- All three groups saturated heavily (~65-68% breach, P50 in the 2.8s range) — this load level may be too severe for any governance strategy to show much daylight; see §5 item 2 for the follow-up this suggests (moderate the load, or increase the rule engine's step size/aggressiveness, and re-test).

**Bottom line (§1e):** the mechanism is now fully validated (real forecasts, real CPU signal, real Rule 1 activations, real replication) — this is a legitimate, defensible result, just not the one the proposal's hypothesis predicted. Report it honestly: modest, real advantage over reactive-only governance; no distinguishable advantage over static allocation at this (severe, ~65-68% baseline breach) contention level.

**§1f — Run 5 (2026-08-13/14, moderated load intensity):** Followed up on §1e's own suggestion — recalibrated `mixed_load.py` down from `N_TIER3=3/interval=5` to `N_TIER3=2/interval=4` (measured 17.8% Static breach in isolation, vs the ~65% the old setting produced in the full harness — this parameter space is quite sensitive to small changes, see the comment in `mixed_load.py`). Recollected telemetry at this new intensity, retrained the LSTM (confirmed working via smoke test — forecast in active use, Rule 1 firing 1.5→4.0 in response to real spikes), and ran a second full 5x-replicated experiment. Pooled results (n≈17,000-19,000 per group — larger than §1e because lighter load means more completed requests per 300s window):

| Group | Mean | P50 | P95 | P99 | Breach% |
|---|---|---|---|---|---|
| Static Allocation | 579.3ms | 9.6ms | 2917.9ms | 2987.9ms | 19.8% |
| Reactive-Only | 501.3ms | 9.6ms | 2902.5ms | 2935.8ms | 17.2% |
| Proactive Hybrid | 564.9ms | 9.6ms | 2930.1ms | 3359.4ms | 18.9% |

- **G1 (Static) → G3 (Proactive): +4.5% breach reduction, 95% CI [0.2%, 8.5%]** — CI does not cross zero: a small but real, statistically defensible improvement over Static. Still nowhere near the ≥30% target.
- **G2 (Reactive) → G3 (Proactive): -10.1% breach reduction, 95% CI [-15.0%, -5.2%]** — CI does not cross zero **in the negative direction**: at this moderated load, Proactive is reliably *worse* than Reactive-only, the opposite of what §1e found under severe saturation.
- Static's rep-to-rep variance was very tight here (19.4%-20.2%, 0.8-point spread — makes sense, it never adapts to anything). Reactive (7.1-point spread) and Proactive (6.1-point spread) were both considerably noisier.

**Synthesis across §1e and §1f — the two properly-replicated, non-confounded results this project has produced:**

| Comparison | §1e (severe, ~65% baseline) | §1f (moderate, ~20% baseline) |
|---|---|---|
| Proactive vs Static | no distinguishable difference | Proactive slightly better (+4.5%, CI excl. 0) |
| Proactive vs Reactive | Proactive slightly better (+3.2%, CI excl. 0) | Proactive reliably *worse* (-10.1%, CI excl. 0) |

**The relative ranking of these three governance strategies is not stable across contention regimes** — this is itself the honest, defensible finding, not a failure. Do not chase a third load-intensity calibration specifically hunting for a setting where Proactive clearly beats both alternatives — that would be post-hoc tuning toward a desired result, not legitimate methodology. Report both regimes as tested, and discuss *why* the ranking flips (candidate explanations: at severe saturation, reactive thresholds fire fast but oscillate/thrash under Reactive-Only's higher variance; at moderate load, the LSTM's 30-step-ahead forecast may be reacting to signal that's already stale by the time the incremental ±0.5 CPU step takes effect, while pure reactive governance benefits from tracking the *current* state more tightly when swings are smaller and more frequent).

**Do not cite any experiment numbers before §1e in anything** — every run before it was measuring a mechanism that either wasn't exercising the governor's actual monitored resource, wasn't properly replicated, or had one of the confounds in §1a-c. §1e and §1f are both valid and should be reported together, not cherry-picked.

**§1g — Rule-engine sensitivity sweep (2026-08-14, single-rep, scoped):** Tested whether §1f's Proactive-worse-than-Reactive result is explained by the rule engine's default step size (±0.5 CPU/±512MB) and cooldown (6 cycles) being too conservative for the LSTM's forecast advantage to matter within a 300s window. `rule_engine.py`'s `CPU_STEP`/`MEM_STEP_MB`/`COOLDOWN_CYCLES` are now overridable via `DG_CPU_STEP`/`DG_MEM_STEP_MB`/`DG_COOLDOWN_CYCLES` env vars (no rebuild needed — this module runs in the host venv). Ran single-rep (`--groups 2,3`, skipping Static since it never touches the rule engine) sweeps at the §1f moderate load intensity:

| Config | CPU step | Cooldown | Reactive breach% | Proactive breach% |
|---|---|---|---|---|
| Default (= §1f) | 0.5 | 6 | 17.2% | 18.9% (worse) |
| Moderate | 1.0 | 4 | 20.1% | 20.2% (tied) |
| Aggressive | 1.5 | 2 | 22.6% | **11.7%** (much better) |

A clean, monotonic trend: as the rule engine reacts faster and more forcefully, Proactive's advantage over Reactive grows substantially — at the aggressive setting it nearly *halves* Reactive's breach rate. This directly supports the hypothesis in §1f's synthesis: the default rule engine was too conservative for the LSTM's 30-step-ahead forecast to translate into real relief before conditions changed again. **This is a single-rep, unreplicated sweep** — a strong, clean directional signal, but not yet a citable result on its own (see §1i for the replication).

**§1i — Aggressive rule-engine config, 5x replicated (2026-08-16/17 — THE STRONGEST RESULT TO DATE):** Replicated §1g's aggressive config (`DG_CPU_STEP=1.5, DG_MEM_STEP_MB=1024, DG_COOLDOWN_CYCLES=2`) properly, 5 reps, Reactive vs Proactive only (`--groups 2,3` — Static reused from §1f since it never touches the rule engine and load/container settings are identical). **Per-rep results were themselves noisy and did not cleanly reproduce §1g's dramatic single-run split** — Reactive: 20.4%/20.2%/17.9%/20.1%/19.7% (tight, 2.5-point spread); Proactive: 20.1%/20.2%/20.1%/**13.0%**/19.6% (7.2-point spread, one standout rep). Despite that noise, the **pooled** result is the strongest finding this project has produced:

| Group | n | Breach% |
|---|---|---|
| Static Allocation | 16,981 | 19.8% |
| Reactive-Only | 17,100 | 19.6% |
| Proactive Hybrid | 18,142 | 18.2% |

- **G1 (Static) → G3 (Proactive): +8.1% breach reduction, 95% CI [4.0%, 12.0%]** — excludes zero.
- **G2 (Reactive) → G3 (Proactive): +7.3% breach reduction, 95% CI [3.1%, 11.2%]** — excludes zero.

This is the **first result in the project's history where Proactive shows a statistically defensible advantage over both Static and Reactive simultaneously.** Still well short of the proposal's ≥30% target, and effect sizes remain small (r≈-0.05 to -0.08, "negligible" by convention at this n), but real and reproducible in direction. Combined with §1h (ablation): the practical implication is that DOCKER-GENIUS's value depends on pairing LSTM prediction with a rule engine tuned aggressively enough to act on it — the default step/cooldown values in the proposal's own methodology (§3.2) were too conservative to realize this benefit.

Ran all 4 configs at the §1f moderate load intensity, default rule-engine settings, single rep each:

| Config | Breach% |
|---|---|
| A — No Semantic + No LSTM (dumb reactive baseline) | 20.4% |
| B — Semantic Only (no LSTM) | **17.9%** |

Coherent with §1f/§1g: **the semantic classification layer alone accounts for essentially all of the observed benefit at default rule-engine settings** — LSTM prediction without semantic gating (C) is indistinguishable from no adaptation at all (A), and adding LSTM on top of semantic awareness (D) doesn't clearly improve on semantic-alone (B). **§1j — Ablation study, 5x replicated at aggressive settings (2026-08-17 — DOES NOT CONFIRM §1h; report honestly):** Ran `run_ablation.py --repeats 5` with the §1i aggressive rule-engine settings (`DG_CPU_STEP=1.5, DG_MEM_STEP_MB=1024, DG_COOLDOWN_CYCLES=2`), same load intensity as all prior runs. | Comparison | Reduction | 95% CI | Excludes 0 |
|---|---|---|---|
| A → D (dumb baseline → full system) | ‑2.9% | [‑7.2%, 1.4%] | No |

The only two comparisons whose CIs exclude zero both show config **B (semantic-only) statistically beating C and D** — i.e., at these aggressive settings, adding LSTM-driven proactive forecasting on top of semantic awareness does not help, and if anything performs slightly *worse* than semantic-awareness alone. This is the opposite of what a "full system wins" narrative would need, and it is not consistent with §1h's single-rep finding either (which showed B≈D, not B>D). **Report this honestly as a non-replication**: properly repeated 5x, the ablation shows no config reliably outperforming the dumb reactive baseline (A) on SLA breach rate, and the semantic-only config (B) is, if anything, the best-performing of the four — a genuinely different and less favorable conclusion than the single-rep first pass suggested.

**Important cross-experiment inconsistency to flag in the paper (Threats to Validity), not silently resolve:** Config B (`reactive`+`semantic_aware=True`) and Config D (`proactive`+`semantic_aware=True`) are *nominally identical* to §1i's Group 2 (Reactive-Only) and Group 3 (Proactive Hybrid) — same mode strings, same rule-engine settings, same load intensity. Yet §1i's pooled Group 2/Group 3 breach rates (19.6%/18.2%, from `governor/experiment/results/group2_kpi.csv`/`group3_kpi.csv`, run 2026-08-16T19:51) do not match this ablation run's Config B/D pooled rates (18.8%/19.9%) — the two nominally-identical experiments even *disagree on which of Reactive/Proactive is better* (§1i: Proactive beats Reactive by 7.3%, CI excludes 0; §1j: Full-System(≈Proactive) is *worse* than Semantic-only(≈Reactive) by 5.7%, CI excludes 0). This is evidence that pooled breach-rate point estimates carry roughly 1–2 points of run-to-run/session-to-session noise beyond what within-run replication captures (possibly host thermal state, Docker daemon state, or subtle load-generator timing differences across separate multi-hour sessions) — this should be stated plainly as a limitation affecting confidence in the exact magnitude of the §1i headline result, not just the ablation.

## 2. Bugs found and fixed (2026-08-10 to 2026-08-12)

| 1 | `governor/experiment/governor_loop.py` | LSTM buffer was fed once per 10s decision cycle, but the model was trained on 1s-interval data (60-step window = 60s). Fixed by adding genuine CPU-bound synchronous computation (`burnCpu()` in `reports.service.ts`) to `bulkGenerate`, gated behind `research_mode`. Bounded by a **fixed amount of work** (loop iterations), not fixed wall-clock time, specifically so completion time genuinely responds to the container's `--cpus` allocation — a `setTimeout`-based delay would not have this property and would defeat the entire premise of vertical CPU scaling. Calibrated to ~3s per call (800M iterations) and verified this measurably blocks concurrent Tier-1 checkouts (Node is single-threaded): produced a 33.6% Tier-1 SLA breach rate in validation, and in a governor smoke test correctly drove Rule 1 to fire 5 times, escalating cpus 1.5→4.0 in direct response to real CPU spikes (93-102%). |
| 11 | `reports.controller.ts` (`bulkGenerate` endpoint) | NestJS's global `ValidationPipe({ whitelist: true })` (`main.ts`) strips any `@Body()` property that isn't declared on a real class with at least one `class-validator` decorator. The endpoint used `@Body() options: { research_mode?: boolean; delay_ms?: number }` — an inline TypeScript type, which has zero runtime reflection metadata — so `options` arrived as `{}` on every single request. | **`research_mode` has been `undefined` (falsy) on every bulk-generate call ever made**, silently disabling anything gated behind it (at the time this was found: the brand-new CPU-burn feature in bug #10, discovered because a calibration test that should have taken >1s completed in 0.6s). Confirmed the JSON body itself was fine (`{"research_mode": true}` sent correctly) — this was purely a server-side stripping bug. Fixed by introducing `BulkGenerateOptionsDto` with `@IsOptional() @IsBoolean()`/`@IsNumber()` decorators and using that as the `@Body()` type instead. **Update (2026-08-17):** the same pattern was found and fixed across 12 more endpoints in `clients`, `auth`, `grun`, `pos`, `inventory`, `grn`, `invoicing`, and `reports.controller.ts`'s own `getFinancialAggregate` — see §5 item 5 for the full fix and empirical verification. |

## 4. Root cause history

**Diagnosed 2026-08-10, fixed 2026-08-12:** train/serve distribution mismatch — the LSTM was trained on telemetry from a moderate-load calibration session (mean CPU 12%, peak 79%) but evaluated under much heavier contention (6 concurrent Tier-3 workers), so it never predicted CPU high enough to cross the 75% scale-up threshold (Rule 1 fired 0 times in the 2026-08-10 Group 3 run). **Fixed** by recollecting telemetry under the same load intensity used for evaluation (`N_TIER1=8, N_TIER3=6, TIER3_INTERVAL=3`) and retraining — confirmed fixed: Rule 1 fired once and the forecast was in active use for 31/37 cycles in the 2026-08-12 run.

**Remaining, as of 2026-08-12:** even with the mismatch fixed, Proactive Hybrid is still significantly worse than Static/Reactive in a single run. This is most likely **not** a mismatch problem anymore — plausible remaining causes, in rough order of likelihood:
- **No replication yet.** Every group so far is n=1. Static's own P99 this run was 5003ms (a few extreme outliers dominating the mean) — this is a noisy, small-sample process, and a single run per group cannot distinguish a real effect from run-to-run variance. This is the single most important gap before drawing any conclusion.
- **Rule engine may be too conservative to react within a 300s window.** Scaling moves ±0.5 CPU / ±512MB per cycle with a 6-cycle cooldown — even when Rule 1 correctly fires, it may take multiple cycles to reach a resource level that actually relieves contention, by which point the window has mostly elapsed. Reactive-only has the same step size but reacts to *current* CPU (no lag from the 30-step-ahead forecast target), which may make it faster to actually reach a useful allocation.
- **Threshold calibration.** 75%/78% may not be well-matched to this workload's actual dynamics — this is exactly the sensitivity analysis the supervisor's checklist already asks for (§5 item 6).
