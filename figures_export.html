FIG. 1 · architecture fig1_architecture.png
Fig. 1. DOCKER-GENIUS system architecture. The Monolith Governor runs entirely outside the monitored erp_app container, observing it through cAdvisor and acting on it only through the Docker Update API — the monitored container is never modified or restarted.
FIG. 2 · workflow fig2_workflow.png
Fig. 2. End-to-end request-to-actuation pipeline, executed continuously while the system is under load: every 10-second decision interval, the most recent 60-second telemetry window is used to forecast the next 30 seconds and update the container's resource allocation before saturation occurs.
FIG. 3 · lstm model fig3_lstm_architecture.png
Fig. 3. Stacked LSTM forecasting model. A 60-step input window of [CPU%, RAM MB] passes through two LSTM layers (64 then 32 units, 0.2 dropout between them) and a dense projection, reshaped into a 30-step joint CPU/RAM forecast.
FIG. 4 · experimental setup fig4_experimental_setup.png
Fig. 4. Three-group experimental design. Identical synthetic traffic (8 concurrent TIER_1 workers, 2 concurrent TIER_3 workers) is replayed against three otherwise-identical stacks, differing only in which governance components are active, so that any measured difference is attributable to the governance mechanism rather than the workload.
FIG. 5 · latency graphs fig5_latency_distribution.png
Fig. 5. TIER_1 request latency distribution by governance strategy, pooled across 5 replicates at the aggressive rule-engine configuration (n ≈ 17,000–18,000 requests per group; log-scaled axis — the bursty tail spans roughly 3 to 3,400 ms). Box shows P25–P75 with the median line; whiskers extend to P0.5 and P99.5.
FIG. 6 · prediction graph fig6_lstm_prediction.png
Fig. 6. LSTM CPU forecast against ground truth on one held-out test window (of 167 total), chosen for its high-variance spike so the forecast behaviour is visible — not the average case (see Table IV for aggregate test-set MAE/RMSE). Shaded region is the 30-step forecast horizon.
FIG. 7 · resource utilization fig7_resource_utilization.png
Fig. 7. Observed CPU utilization and the governor's allocated CPU cores over one representative 300-second Proactive Hybrid run, with each scaling decision annotated by the rule that fired. cpus falls to 1.0 during an initial idle cooldown, then Rule 1 escalates it twice as TIER_1 load rises, and Rule 4 later trims memory once the forecast confirms headroom is no longer needed.
